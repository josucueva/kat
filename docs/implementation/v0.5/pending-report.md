# v0.5 Implementation Pending Report

This report outlines the remaining work for KAT v0.5. **Phases 10 and 11 are frozen. Phase 12.0–12.5 remote design, local implementations, authenticated workflows, and CLI contract review are complete locally; deployment verification remains pending. Phase 13 migration remains pending. Phase 14's coverage audit and scenario specification are committed in `62ef064`; the existing workspace test, format, and Clippy baseline passed on 2026-10-25. SYS-01..SYS-05 remain unexecuted pending Phase 13 and the user-path prerequisites in [system-acceptance.md](system-acceptance.md).**

All core reconciliation, conflict resolution, topology traversal, and collaboration CLI workflows have been successfully implemented and tested. This includes:

- Phase 4: `WorkspaceBackend` Git trait mapping

- Phase 6: Core Validation

- Phase 10.10: JSON machine interfaces for the collaboration commands, with v1 envelope contract and MI-COL checks.
- Phase 10.11: Ten local collaboration E2E scenarios through separate `kat` processes, covering clean and conflicted merges, semantic resolution without materialization, physical edits, abort, advance, switch, restart, and NamedReference preservation. The version-1 session format gained an optional clean physical snapshot ID; older sessions recover it from immutable inputs only. Candidate state and Git protection refs are checked across restart and after cleanup.
- Phase 11.1: Frozen transport abstraction with semantic/workspace separation, recursive closure verification, parent-first uploads, closure-complete unnamed-tip discovery, per-reference tracking CAS outcomes, and a documented retention contract. Reported verification: 631 workspace tests and 16 remote tests pass.
- Phase 12.3 (`8a02b56`): Added `TrustedHubSemanticTransport`, a file-backed local Hub core. It stores exact canonical object bytes by repository and object ID, persists KAT named refs with per-name CAS, fixes each repository to one controlled Git backend, and checks policy, semantic closure, and snapshot trees before CAS. Discovery advertises only verified unnamed tips and fails closed for invalid named refs. Five Hub acceptance tests cover interrupted upload/retry, missing dependencies, backend/policy drift, concurrent CAS, reopen, and coordinator publish/fetch. Full gate: 649 tests plus build, formatting, and Clippy passed.
- Phase 12.4 (`bd3eb73`): Added one loopback integration acceptance test composing the real `RemoteCoordinator`, file-backed Hub, controlled Git server, and `GitWorkspaceTransport`. It publishes a revision with semantic and physical changes, reopens Hub and Git transports, and fetches into a second initialized KAT repository. It verifies rejection of missing physical content and backend mismatch, interrupted transfer with retry, stale CAS, exact semantic-object transfer, and preservation of the receiving local ref, accepted state, workspace base, active lineage, and working tree. Full gate: 650 tests, build, formatting, and Clippy passed.
- Phase 12.5 design (`899aa57`, frozen in `0b1f5c8`): [phase12-service-design.md](phase12-service-design.md) defines HTTPS JSON for the frozen `SemanticTransport`, repository-bound read/publish bearer capabilities with semantic/Git audiences and expiry, shared authorization and revocation behavior, independently authorized Git discovery and pack requests, secret handling, and AUTH-01..18.
- Phase 12.5.1 (`d991db4`): Added a shared verifier for the Hub and Git audiences, hash-only grant storage, per-request repository/scope/expiry validation, constant-time token digest comparison, and fail-closed policy reload. Loopback HTTP tests cover missing, expired, wrong-repository, wrong-scope, publish-implies-read, audience separation, revocation, and policy recovery. Full gate: 654 tests, build, formatting, and Clippy passed.
- Phase 12.5.2 (`25c315e`): Added `HubHttpService` and `HttpSemanticTransport` without changing the `SemanticTransport` trait. Both service boundaries can share one `Arc<AuthorizationVerifier>`. Real loopback HTTP acceptance tests cover read/publish access, reference and object operations, stale CAS, wrong-repository hiding, invalid object/closure rejection, URL and query credential rejection, and credential-safe errors; size and rate limit boundary checks cover request caps. The endpoint uses HTTPS-only client URLs, certificate validation, redirects disabled, a 30-second timeout, and runtime-only tokens. Full gate: workspace build/tests, fmt, Clippy, and generated assets passed. The listener still depends on a trusted TLS proxy configured for one request per upstream connection.
- Phase 12.5.3 (`743f2de`): Added `GitHttpGateway` for one fixed controlled backend, with shared-verifier Basic authentication on both smart HTTP discovery and pack operations. The gateway rechecks backend binding/retention policy per request, invokes `git http-backend` with a fixed backend path, limits request and response packs to 256 MiB, and retains the create-only lineage hook. `GitWorkspaceTransport` now accepts a runtime HTTPS token via libgit2 credentials, rejects credential/query URLs, disables redirects, and keeps the token out of persisted config. Seven loopback tests use real libgit2 HTTP fetch/push and cover grants, expiry/revocation shared with Hub, wrong repositories, binding mismatch, ref mutation rejection, and size limits. Full gate: formatting, build, workspace tests, Clippy, and generated assets passed. The instance handles requests serially and buffers request/response bodies; the proxy, Git executable/PATH, and backend must remain within the deployment trust boundary.

- AUTH-17/18 (`8712523`): Added Unix loopback acceptance tests composing `RemoteCoordinator`, authenticated Hub HTTP, and authenticated Git smart HTTP. AUTH-17 publishes semantic and physical changes with publish access, reopens clients, then fetches with read access into a second repository; complete closure, tracking references, and preservation of local refs, accepted state, workspace base, active lineage, and working-tree bytes are checked. AUTH-18 transfers physical snapshots and one canonical object, then revokes publish access so the next real Hub HTTP object upload receives `403`; no named ref advances. Wrong-repository grants, read-only publication, shared Hub/Git revocation, authorized retry, and stale CAS are also checked. Full workspace tests, build, formatting, Clippy, and generated-asset checks pass. This is loopback evidence, not deployed TLS or retention proof.
- Step 12.5.4 (`11e47b8`) remote CLI workflows, hardened by `54bbaa4`: Added `remote add/list`, `fetch`, `push`, and `sync`. Named remotes persist only HTTPS endpoints and repository/backend identities; `KAT_REMOTE_TOKEN` and optional `KAT_REMOTE_CA_FILE` are runtime-only. Push publishes the current clean workspace base revision only when its semantic state matches the accepted state and the working tree is clean. Existing remote targets must be ancestors of the candidate; the observed target remains the CAS expectation to catch later races. Hub operations are scoped to the configured local `RepositoryId`, and Git snapshot operations verify the live backend marker. Fetch and sync preserve local authority, partial tracking outcomes retain all fields in versioned JSON, and topology output distinguishes `Same`, `LocalAhead`, `OtherAhead`, `Diverged`, `AmbiguousMergeBase`, and `Unrelated`. Separate-process tests cover remote persistence, authenticated end-to-end publication and fetch, stale CAS, non-fast-forward rejection, live backend mismatch, partial tracking updates, invalid and revoked credentials, read-only push denial, and local authority preservation. The focused CLI suite and full workspace verification passed; formatting, build, Clippy, and generated assets are clean. Deployment TLS/proxy isolation, direct-backend access control, retention, and durability remain unverified.
- Phase 14 coverage audit (`62ef064`): Mapped UC-001..UC-008, invariant coverage, and existing tests into SYS-01..SYS-05. The current baseline passed `cargo test --workspace`, `cargo fmt --check`, and `cargo clippy --workspace --all-targets -- -D warnings` on 2026-10-25. No system workflow is marked passed. ### Phase 11: Remote abstraction — Complete

Step 11.1 satisfies the Phase 11 acceptance criteria. The implementation plan contains no separate 11.2 repository workflow step; actual remote-backed `sync`/`push` is assigned to Phase 12. No additional wrapper around `RemoteCoordinator` is planned because it already coordinates the existing local stores and injected transports.

### Phase 12: KAT Hub and Git remote integration
**Status:** Local implementation and authenticated CLI workflow complete; deployment acceptance remains pending.
- Design: [`phase12-transport-design.md`](phase12-transport-design.md), drafted in `6f03dd3` and reviewed/amended in `0ee8b36`, defines canonical-byte transfer, Git lineage refs, publication ordering, repository binding, and recovery. The transport contract is frozen independently of deployment proof. The retention guarantee requires a KAT-controlled Git backend with server-enforced create-only lineage refs, remote read-back/tree verification, and Hub-side verification of the bound backend before CAS.
- Phase 12.1 is complete in `2989582`: local snapshot recording requires the embedded Git repo and a verified direct protection ref, mapping updates are atomic, and lookups reject missing or mismatched protection refs. Missing-repository, conflicting/missing-ref, and recovery cases pass; the full build, test, formatting, and Clippy gate passed.
- Phase 12.2.1 is complete in `facf800` and tracked in `32d1de8`: the controlled bare backend binds one repository and backend ID, and its receive hook allows lineage-ref creation while rejecting updates, deletions, and non-lineage writes. Loopback tests cover binding mismatch, policy drift, and client mutation rejection.
- Phase 12.2.2 is complete in `1f5d8e2`: the concrete Git `WorkspaceTransport` saves one immutable destination, verifies the remote's advertised repository/backend binding marker, transfers only lineage refs, and recomputes `WorkspaceSnapshotId` from trees read back into a fresh repository. Seven loopback integration tests pass, including wrong binding/tree rejection and fetch without materialization. The full build, test, formatting, and Clippy gate passed.
- Phase 12.2.3 is complete locally in `517e102`: a failed second representation leaves the first immutable ref intact and retry succeeds; concurrent identical publications are idempotent; aggressive GC during a paused receive rejects the in-flight upload without creating a ref; retry then succeeds, and a published snapshot remains fetchable after `git gc --prune=now`. Invalid fetched trees leave no local representation or staging ref. The full build, test, formatting, and Clippy gate passed.
- Phase 12.3 is complete locally in `8a02b56`: the trusted Hub core implements `SemanticTransport`, immutable canonical storage, repository-scoped named-ref CAS, closure-verified discovery, fixed Git backend binding, and policy/closure/tree checks before CAS. Five Hub tests pass. Its `RemoteCoordinator` publish/fetch test uses a test `WorkspaceTransport`; the Hub independently verifies a real controlled bare Git repository. Full gate: 649 tests, build, fmt, and Clippy pass.
- The deployment trust boundary covers ordinary Git clients and supported maintenance operations. Unrestricted host administrators and underlying storage loss are trusted deployment risks; the service must state its durability and recovery assumptions.
- GitHub's fully qualified ref API and documented branch/tag rulesets do not prove retention for `refs/kat/*`. This repository's `origin` is only its project-source remote, not evidence of a configured KAT workspace host.
- Phase 12.2 local implementation is complete. Its loopback backend and transport are not deployment proof. Phase 12.3 verifies the controlled backend's local policy files/configuration and reads snapshot refs and trees before CAS, but this does not verify production service startup, host controls, backups, or storage durability.
- The trusted Hub core remains in-process code; the HTTP adapter and CLI do not provide production TLS termination or deployment provisioning. The Hub data root must be protected by deployment operating-system permissions; the library does not configure ACLs. Do not expose the raw Hub core to untrusted processes.
- Phase 12.5.4 remote CLI workflows are complete locally. Deployment TLS proxy isolation, direct Git bypass prevention, retention, and storage durability remain separate acceptance gates.
